# 楼栋外墙渗水季节复查系统

物业完成外墙维修后，必须在**有效的雨后条件**下回到住户原位置复查，才能判定渗水是否真正解决。
本系统管理「住户报修 → 维修施工 → 雨后复查 → 住户异议」的完整闭环。

## 一条命令启动

```bash
./run.sh          # 构建前端 + 后端并启动，访问 http://localhost:8080
./run.sh fresh    # 清空数据库/照片，恢复演示种子后启动
```

要求 JDK 21+、Node.js 18+、Maven（若系统无 Maven/JDK，脚本也支持把它们解压到 `~/opt` 下使用）。
首次启动会自动安装前端依赖。

- 后端：Java + Quarkus（REST / Hibernate ORM with Panache / SQLite）
- 前端：Svelte + Vite，构建产物由 Quarkus 作为静态资源托管（单端口 8080）
- 数据库：本地 SQLite，文件在 `data/leak.db`；照片保存在 `data/photos/`
- 天气：本地模拟（页面顶部「本地模拟天气」直接登记/删除降雨）

## 业务规则

1. **住户报修**：标明楼栋、立面、房间、渗水位置并上传照片。
2. **同点位关联**：楼栋 + 立面 + 位置相同的报修自动归为同一渗水点位，联合施工、
   共用雨后复查条件；**各住户的报修与复查记录独立保留**。
3. **复发报修**：同一户对同一位置再次报修，自动记为原问题复发（第 N 次报修）；
   若该点位此前已验证修复，标记为「解决后再漏」并重新打开点位，历史处理过程可在详情页查看。
4. **雨后复查（核心）**：施工完成后报修单进入「待复查」。只有出现
   **降雨量 ≥ 10mm 且降雨日期严格晚于施工完成日**的有效降雨，才允许复查通过；
   施工当天的降雨不算。未满足条件时，前端禁止提交、后端也会拒绝，任务保持待复查。
   复查「仍有渗水」则退回待维修，重新施工后需再次等待有效降雨。
5. **异议闭环**：住户不认可已验证结论可提异议（附照片），物业回复并选择
   「维持原结论」或「重新安排处理」。

详情页按 **报修 → 施工 → 复查 → 异议** 的时间线排列各阶段照片与结论，
并展示同点位关联报修与本户复发历史。

## 演示种子（首次启动自动生成，日期相对当天）

| 场景 | 数据 |
| --- | --- |
| **同点位关联 + 未达复查条件** | 3栋东立面 12层主卧窗上角，1202 张伟、1203 王芳两户关联报修，2天前完成施工，昨天仅 4mm 小雨 → 两单均保持「待复查」，无法验证 |
| **复发报修** | 7栋南立面次卧窗台，301 陈强的报修曾在大雨后验证修复，近日同一位置再次漏水 → 自动生成「第2次报修·解决后再漏」，详情页可查看上一轮施工与复查 |
| **住户异议** | 5栋西立面顶板，806 刘洋已验证后提出异议 → 「异议处理中」，等待物业回复 |

页面顶部登记一场 ≥10mm、晚于施工日的降雨（如模拟今天暴雨），
3栋两户的「雨后复查」按钮即可使用，复查通过后变为「已验证修复」。

## 主要接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/reports` (multipart) | 住户报修，自动关联/识别复发 |
| GET | `/api/reports` / `/api/reports/{id}` | 列表 / 详情（含时间线、关联、复发链） |
| POST | `/api/reports/{id}/repairs` (multipart) | 记录施工，关联单进入待复查 |
| POST | `/api/reports/{id}/rechecks` (multipart) | 雨后复查（未达雨后条件返回 400） |
| POST | `/api/reports/{id}/objections` (multipart) | 住户提异议 |
| POST | `/api/objections/{id}/reply` (JSON) | 物业回复异议 |
| GET/POST/DELETE | `/api/weather[/rain/{id}]` | 模拟天气与降雨记录 |
| GET | `/photos/{fileName}` | 读取本地照片 |
